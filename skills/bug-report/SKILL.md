# 버그 리포트 (개발자 핸드오프)

> 한국어 산문은 `deslop` 스킬의 규칙(존재·이해·구조·표현 4축)을 적용해 쓰고, 내보내기 직전에 `slop-audit` 게이트를 통과시킨다.

## 핵심 원칙
목표는 **개발자의 인지 에너지를 가장 뾰족하게 쓰게 하는 것.** 개발자가 더 잘하는 일(쿼리 작성·코드 추적·해법 설계)을 대신 해주지 말고, **그들이 봐야 할 지점을 정확히 가리켜라.**

문제 대응 순서는 **(1) 증상 그대로 → (2) 원인 추정 → (3) 원인 발견 → (4) 해결**. 리포트가 반드시 줘야 하는 건 **(1) 증상(+발견 경위+고객 불편)**과 **재현(가능하면)**. (2)(3)(4)는 개발자가 어차피 다시 검증하므로 **선택**, 적더라도 "가설"로만.

**왜 (1)이 필수인가**: 원인·해법만 온 티켓은 개발자가 맞는지 검증 못 하고 누락된 원인도 못 본다. (1) 날것의 증상이 있어야 (2)를 대조하고 (3)의 빠짐을 잡는다. (1)에 원인·해석 섞지 말 것.

## 리포트 구조 (이 순서 고정)

### 1. 증상 & 고객 불편 & 발견 경위 (필수)
- **증상 = 드러난 현상 그대로**, 관측 사실만. 평문 1~2문장 "무엇이 이상하고 → 고객/현장이 뭘 겪나". 규모(빈도·영향) 한 줄.
- **발견 경위 한 줄**: 어쩌다 발견했는지. 개발자가 맥락·범위를 잡음.
- 원인·해석 섞으면 실격. 고객 불편 빼면 실격.

### 2. 재현 (있으면 필수 — 유저 행동 단위)
- **제품에서 유저가 하는 행동 순서**로: "유저가 A→B→C 하면 → 이 결과." 개발자가 앱/dev에서 밟을 수 있게. 실제 관측 사례의 여정을 그대로 재연하면 최선.
- **비결정적이면 그렇다고 말하라**: 부분 실패·경쟁조건처럼 유저 행동으로 결정적 재현이 안 되는 버그는, 억지 시퀀스 만들지 말고 "결정적 재현 불가 + 발생 조건 + 관측된 실례"로 넘긴다.
- 🚫 **상상 금지.** 시스템 실제 동작(코드·상태전이)을 확인한 뒤에만 쓴다. 추정 재현은 개발자가 즉시 간파해 리포트 전체 신뢰가 무너진다.

### 증거 (별도 블록, 필수) — 쿼리 말고 "봐야 할 것"
- **개발자가 자기 도구로 바로 열어볼 수 있는 구체적 실례**를 준다: 대상 ID·엔티티·타임스탬프, 기대 vs 실제. 
- 🚫 **쿼리·조사 절차를 대신 써주지 말 것.** SQL 덤프는 개발자가 더 잘 짠다 — 인지 에너지를 낭비시키고 리포트를 장황하게 만든다. "이 예약 ID를 보면 세차권이 없다"까지만, "이 쿼리 돌려라"는 넣지 않는다.
- firsthand 확인한 값만 확정으로.

### 3. 원인 가설 (선택 — "가설"로 명시)
자문 2개 통과 표시: **실제 원인인가? 유일한 원인인가?** 여러 갈래면 갈래별로. 코드 위치는 "검증 요망". 확정 안 된 건 "미확정"으로 정직하게.

### 4. 해법 제안 (선택 — "제안"으로 명시)
자문 2개: **정말 고치나? 이 현상만 국소로 때우는 게 아니라 같은 구조의 다른 문제도 잡나?** 국소/구조 나눠서.

## 확신 위장 금지
firsthand 데이터/재현은 확정. 3·4는 개발자가 재검증하므로 가설/제안으로만. 코드 인용 provenance 밝히기. 모르면 "미확정"이라 쓰는 게 틀린 확신보다 낫다.

## 자주 하는 실수
| 실수 | 교정 |
|---|---|
| 쿼리·조사 절차를 대신 써줌 | 개발자가 더 잘함. 봐야 할 케이스(ID)·지점만 가리켜라 |
| (2)(3)만 쓰고 (1) 증상 누락 | 개발자가 원인 검증·누락 확인 못 함. 날것 증상 먼저 |
| 증상에 원인·해석 섞음 | (1)은 관측 사실만. 섞으면 검증 기준 오염 |
| 발견 경위 누락 | 어쩌다 발견했는지 한 줄 |
| 말과 기술용어를 한 문단에 섞음 | 상황=평문, 증거=별도 블록 |
| 고객 불편 누락하고 기술현상만 | "고객/현장이 뭘 겪나"를 1번에 |
| 원인·해법을 사실처럼 단언 | 3·4는 가설/제안. 미확정은 미확정으로 |
| 비결정적 버그에 억지 재현 시퀀스 | 결정적 재현 불가라고 명시 + 조건·실례 |

## 게시 전
외부(Linear/Slack/Notion) 쓰기는 목적지·발행 명시 확인 후. 관련: [[feedback_handoff_separate_situation_from_evidence]], [[feedback_confirm_before_external_writes]], [[feedback_bug_ticket_not_feedback_skill]].

리포트가 길어져 문서/아티팩트로 만들 땐 /writing 스킬의 "요지 카드 + 토글" 구조(역피라미드, 토글 안 열고 2~3분)를 따른다 — 순차 서술형 긴 리포트는 개발자도 중간에 포기한다.
