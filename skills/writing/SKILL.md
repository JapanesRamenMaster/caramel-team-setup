# 글쓰기 원칙

문서를 쓸 때 반드시 이 원칙을 따른다. /feedback 스킬(팀원 작업물에 피드백할 때)과는 별개로, 사용자가 직접 작성하거나 전달하는 모든 문서에 적용한다.

## 핵심: 논점 중심으로 쓴다

만연한 정보의 나열은 보는 사람이 짜증난다. 모든 문서는 아래 구조를 따른다:

1. **결론/주장을 먼저 쓴다** — "우리는 A에 월 X를 쓰고 있다. 문제는 두 가지다."
2. **왜 문제인지 쓴다** — "이걸 안 잡으면 150명 규모에서 월 385만원이 된다"
3. **어떻게 하면 되는지 쓴다** — "지금 잡으면 105만원. 연 3,360만원 차이"
4. **확인해야 할 것만 남긴다** — "채널톡 청구서 내역 확인 필요"

## 절대 하지 않는 것

- **궁금하지 않은 배경 설명** — 이미 아는 맥락을 장황하게 반복하지 않는다. 예: "Anthropic API는 팀 전체 Claude 초대 + 연간 계약 전환에 따른 일시 결제분으로..." 같은 걸 매 섹션마다 반복하면 짜증남
- **에지케이스를 본론처럼 쓰기** — 일회성 지출이나 특수 상황은 한 줄로 언급하고 넘어간다. 본문에서 반복하지 않는다
- **카테고리별 총정리** — 읽는 사람이 원하는 건 "뭐가 문제이고 어떻게 하면 되는지"이지 "카테고리 A는 얼마, B는 얼마, C는 얼마"가 아니다
- **같은 정보를 다른 형태로 반복** — 표로 보여줬으면 텍스트로 다시 설명하지 않는다
- **"~하는 것이 좋겠습니다" 같은 문어체** — 기계적이고 딱딱하다

## 구조 원칙

### 요약은 진짜 요약이어야 한다
- 3줄 이내로 상황 + 핵심 문제 + 임팩트
- 상세 표는 요약 바로 아래에 한 번만
- 요약만 읽어도 뭘 해야 하는지 알 수 있어야 한다

### 본문은 논점별로 쓴다
- "인원 비례 과금: 지금 잡아야 하는 것" → "정액제: 요금 구조가 이상한 것" 같이 논점이 제목이 된다
- "Google Workspace", "flex", "채널톡" 같은 서비스명은 제목이 아니라 논점 안에 들어간다
- 각 논점 안에서: 뭐가 이상한지 → 왜 문제인지 → 어떻게 하면 되는지 → 확인할 것

### 표는 비교할 때만 쓴다
- "현재 vs 조정 후" 같이 비교가 필요할 때만 표를 쓴다
- 단순 나열은 불렛이나 줄글로 충분하다
- 같은 데이터를 표 + 텍스트로 이중 표현하지 않는다

## 숫자 원칙

- **연간 결제는 12로 나눠서 월비용으로 환산한다** — 일시금 그대로 쓰면 월비용 비교가 안 된다
- **에지케이스(일시금, 환불 등)는 별도로 빼고 정상 월비용을 기준으로 쓴다**
- **절감액을 쓸 때는 근거를 바로 옆에 쓴다** — "월 52만 (65명 x 8천원)"
- **숫자는 빌링 실데이터 기준이다** — 추정치라면 "추정"을 명시한다
- **스케일업 시나리오를 반드시 넣는다** — 인원 비례 과금은 현재 + 100명 + 150명 등 규모별 비용을 표로 보여준다

## 톤

- /feedback 스킬의 톤 규칙을 따른다 (존댓말 + 캐주얼 혼합)
- "~거든요", "~인데요", "~해요", "~합니다"를 자연스럽게 섞는다
- 평서형 "~다" 종결(번역체/기계체)은 사용하지 않는다
- 경영지원팀 등 타 팀에 전달하는 문서에서도 같은 톤을 유지한다

## 포매팅

- `~` 문자를 쓰지 않는다 (노션에서 취소선으로 렌더링됨). 범위는 `-`로, 약(approximately)은 "약"으로 표기
- `---` 가로줄을 쓰지 않는다
- 이모지를 쓰지 않는다
- 컬러코딩은 `gray_bg` 하나만 사용하거나 아예 안 쓴다
