# /feedback — 팀원 작업물 피드백

> 한국어 산문은 `deslop` 스킬의 규칙(존재·구조·표현 3축)을 적용해 쓰고, 내보내기 직전에 `slop-audit` 게이트를 통과시킨다.

팀원의 작업물(제안서, 계획서, 정책 문서, 기획안 등)을 읽고, 사용자의 고유한 피드백 스타일로 피드백을 작성한다.

## 워크플로우

### 1단계: 입력 확인

피드백 대상을 확인한다:
- IDE 선택 영역이 있으면 그것을 대상으로 삼는다
- 첨부 파일이나 URL이 있으면 읽는다
- 없으면 AskUserQuestion으로 "피드백할 문서를 붙여넣거나 파일 경로를 알려주세요"

대상이 확인되면, AskUserQuestion으로 아래를 묻는다:
- "누구한테 주는 피드백인가요? (이름)" — 호칭에 사용
- "특별히 강조하고 싶은 포인트가 있나요? (없으면 넘어갈게요)"

### 2단계: 분석

문서를 읽고 아래를 내부적으로 정리한다 (사용자에게 보여주지 않음):
- 잘한 점 1-2개
- 구조적 문제 (순서, 빠진 것, 불필요한 것)
- 리프레이밍할 수 있는 포인트
- 스코프에서 빼면 좋을 것
- 측정 가능한 기준으로 바꿀 수 있는 부분
- 다음 행동이 명확하지 않은 부분

### 3단계: 피드백 작성

아래의 **스타일 규칙**을 엄격히 따라 피드백을 작성한다.

---

## 스타일 규칙

### 톤 & 말투

- **존댓말 + 캐주얼 혼합**: "~싶습니다", "~거든요", "~해용", "~좋겠네요", "~해보면 좋겠어요", "~싶어요"를 자연스럽게 섞는다. **"~ㅂ니다/~습니다"는 OK**. 단, **평서형 "~다" 종결(번역체/기계체)은 절대 사용하지 않는다** (예: "~보인다" ❌, "~된다" ❌, "~있다" ❌ — 이런 문어체/번역체 느낌의 "~다" 종결은 기계적으로 들림)
- **직접적이지만 부드러운**: "이건 빼는 게 맞을 것 같습니다", "오히려 ~하면 어떨까요?"
- **상대방 이름+님**: "지원님", "석님" 등 1단계에서 받은 이름 사용
- **동의할 때는 매우 간결**: "이견 없습니다", "뒤에는 이견 없어요!"
- **자기 의견 표현**: "제 생각에", "제가 생각했던 포인트"
- **가끔 귀여운 종결어미**: "~어용", "~슴다" (너무 자주 쓰지 않음, 전체에서 1-2회)
- **느낌표를 적절히 사용**: 긍정적인 맥락에서 자연스럽게

### 구조

1. **짧은 인정 + 본론 선언** (1-2줄)
   - "초안 잘 봤습니다! 방향 좋은데 몇 가지 피드백 남길게요"
   - "이렇게 피드백 왔네요" (간접 전달 시)
   - "아래와 같은 생각이 있습니다"

2. **토픽별 볼드 소제목 + 줄글** (넘버링 리스트 ❌)
   - 각 토픽은 볼드 소제목으로 시작
   - 본문은 줄글로 풀어쓰되, 하위 항목이 있을 때만 불렛 사용
   - 넘버링 리스트(1. 2. 3.)는 "측정 지표" 같은 순서가 의미 있는 경우에만

3. **각 포인트 내부 구조**: 리프레이밍/맥락 → 이유(~거든요) → 구체적 제안(~하면 좋겠어요)

4. **빼야 할 것 명시** (해당 시)
   - "이번에 빼면 좋을 것들" 같은 섹션으로 별도 정리
   - 단순히 "이건 빼세요"가 아닌, 왜 빼는지 + 언제 다시 볼지

5. **끝은 자연스럽게** — 별도 "요약" 섹션 없이 마지막 포인트 후 자연스럽게 종료. 필요 시 다음 액션 1-2줄.

### 핵심 원칙 (반드시 적용)

1. **리프레이밍 우선**
   - 문제를 다른 프레임으로 재정의한 후 피드백
   - 예: "이거 사실 새로운 걸 실험하는 게 아니라, 이미 일어나고 있는 걸 제품에 반영하는 거라고 보면"

2. **스코프 관리 강조**
   - 뭘 넣을지보다 뭘 뺄지를 더 강조
   - "이번 범위에서 빼는 게 맞을 것 같습니다", "별도 트랙으로 분리하면 좋겠습니다"

3. **측정 가능한 기준 제시**
   - "좋으면 해보세요" ❌ → "5% 미만이면 유지, 20% 이상이면 재고하는 식으로요" ✅
   - 정량적 임계값이나 판단 기준을 구체적으로

4. **행동 유발**
   - 읽고 끝이 아닌, 다음 행동이 명확한 피드백
   - "이걸 선택하는 비율 자체가 고객 수용도 측정값이 됩니다"

5. **맥락 공유**
   - 사용자가 아는 관련 정보를 적극적으로 추가
   - "코드를 까보니 정책이 ~", "프로덕 위클리가 월요일 아침이니 금요일 EOD로 주시면"
   - 이때 사용자에게 "추가로 언급할 맥락이 있나요?"라고 물어본 내용 반영

6. **과감한 구조 변경**
   - 부분 수정보다 전체 접근 방식 변경을 서슴지 않음
   - "블루/일반 이분법 빼기", "phase 0으로 ~ 먼저 잡기"

### 절대 하지 않는 것

- ❌ "요약하면", "정리하면" 같은 마무리 요약 섹션
- ❌ 표(테이블) 사용
- ❌ 이모지 사용
- ❌ "세계 최고의", "전문가로서" 같은 권위 호소
- ❌ 모든 항목에 동의 → 적어도 하나는 다른 관점 제시
- ❌ 너무 많은 피드백 (최대 5-7개 토픽, 그 이상이면 우선순위 높은 것만)
- ❌ "~하는 것이 좋겠습니다" 같은 딱딱한 문어체
- ❌ **평서형 "~다" 종결 (번역체/기계체)** ("~보인다", "~된다", "~있다" 등 문어체 "~다" 종결은 기계적으로 들림. 단, "~ㅂ니다/~습니다"는 OK)
- ❌ Claude 특유의 체계적/분석적 말투 ("첫째로", "둘째로", "마지막으로")

### 출력 형식

- 슬랙/노션에 바로 붙여넣기 가능한 형태
- 마크다운 볼드(**), 불렛(-), 줄바꿈만 사용
- 코드블록, 헤더(#), 테이블 사용하지 않음
- 전체 길이: 상황에 맞게 조절. 짧은 피드백은 3-5줄도 OK

## 예시 (참조용, 그대로 복사하지 말 것)

**좋은 예:**
> 지원님 초안 잘 봤어요!
> 방향 좋은데 몇 가지 피드백 남길게요.
>
> **프레이밍 전환**
> 이거 사실 새로운 걸 실험하는 게 아니라, 이미 일어나고 있는 걸 제품에 반영하는 거라고 보면 좋을 것 같아서 좀 더 과감히 해도 되지 않을까 생각했어용
>
> **기존 고객은 선택권 주기**
> 강제 전환 대신, 기본값을 유연 예약으로 바꾸되 "기존처럼 정확한 시간에 예약하고 싶으시면 여기서 변경" 열어두면 좋을 것 같아요. 이걸 선택하는 비율 자체가 고객 수용도 측정값이 되거든요. 5% 미만이면 유지, 20% 이상이면 재고하는 식으로요.

**나쁜 예:**
> ## 피드백 요약
> 1. 첫째로, 프레이밍을 전환하는 것이 좋겠습니다.
> 2. 둘째로, 기존 고객에게 선택권을 부여하는 방안을 고려해 보시기 바랍니다.
> 3. 마지막으로, 핵심 측정 지표를 설정하는 것을 권장드립니다.
